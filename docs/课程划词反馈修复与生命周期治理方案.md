# 课程划词反馈效果链修复与反馈生命周期治理方案

> 状态：**已按用户确认实施（阶段 A–C 核心范围）**  
> 研究日期：2026-08-28  
> 实施日期：2026-08-28  
> 验证：后端 173 passed；前端 Vitest 5 passed；tsc 通过；Vite/Rolldown 在 2249 modules 后既有 Windows 原生 exit 1  
> 适用范围：课程正文划词反馈、AI 伴学“小节整体修改”、课程反馈优化规则  
> 项目约束：个人本地版；不建设管理后台、不做平台化；真实课程数据不得用测试脚本清理

## 1. 背景与本次问题复现结论

用户在故事版课程的“课前准备”中划选了一道综合问题，实际反馈是“对于第一节——课前准备来说，这个问题出现在这里是完全多余的，请你删去”。提交后界面只显示提交成功，没有出现“修改前 / 修改后（删除）”预览，也没有“确认删除”。

本次研究核对了当前源码、未提交工作区改动、运行中的后端进程与该课程最新反馈记录。可以确定：

1. **当前源码本来已经设计了完整效果链**：提交反馈 → 生成删除/改写候选 → 前端对比预览 → 用户继续修改或确认 → workspace 落盘并立即刷新。
2. 最新真实反馈 `cfb_20260828155736_cac2e143` 已成功完成分析，状态是 `analyzed`，也生成了正确的诊断和“课前准备不放综合比较题”规则；但记录中没有 `rewriteSession` 和 `latestProposal`，因此前端没有候选可供确认。
3. **本次直接根因已经定位**：`generate_rewrite_proposal` 的确定性删除词表包含“删除、删掉、去掉、移除、不要这段、不需要这段”，却漏掉了用户实际使用的“删去”。所以请求没有走空文本删除候选，而是误入普通 LLM 改写分支。对于明确要求删除的反馈，模型很可能返回空改写或其他不满足 `rewrittenText` 契约的结果，随后被捕获为 `rewriteError`；该错误目前不会写回 feedback 记录，所以日志只看得到 analysis、看不到失败详情。
4. 前端在无 proposal 时使用 `result.message || result.rewriteError`；由于分析阶段必定提供 `message`，真正的 `rewriteError` 被“课程意见已记录，并已更新课程语言优化库”覆盖。因此用户只看到提交成功。这与真实记录“已 analyzed 但无 rewriteSession”完全吻合。
5. 项目另有中文路径下 uvicorn `--reload` 不可靠的已知风险，验收时仍必须显式重启并核对 worker 时间；但当前 worker 启动晚于 service 文件修改时间，**不能把旧 worker 当成本次唯一或首要根因**。

结论：该功能不是完全没有实现，而是“**删除意图词表漏掉‘删去’ + 候选失败被成功文案遮蔽 + 失败不可重试/会话不可恢复**”共同造成了用户看到的“只提交、不修改”。

## 2. 当前完整效果链

### 2.1 前端划词与结构定位

主要文件：

- `web/src/components/SelectionToNoteToolbar.tsx`
- `web/src/hooks/useTextSelection.ts`
- `web/src/components/ModuleView.tsx`
- `web/src/App.tsx`
- `web/src/api.ts`、`web/src/apiClient.ts`
- `web/src/types.ts`

链路：

1. `useTextSelection` 捕获页面选区。
2. `SelectionToNoteToolbar` 读取选区及周边 DOM。
3. `feedbackContextFromSelection` 记录：
   - 前文、后文、所属块全文；
   - task/module/knowledge point；
   - `sourceArea`；
   - 精确字段 `field`；
   - `sectionKind`、`itemIndex`；
   - 跨多个字段时的 `selectionFragments`。
4. `ModuleView.tsx` 用 `data-course-feedback-scope` 和 `data-course-feedback-field` 提供锚点。故事版课前准备使用：
   - scope：`story_preparation`；
   - field：如 `storySection.narrative`、`storySection.questions`；
   - 列表项使用 `itemIndex`。
5. 用户提交后由 `App.handleSubmitCourseFeedback` 绑定当前 course ID，调用 `POST /api/courses/{course_id}/course-feedback`。

### 2.2 后端分析、规则提炼和候选生成

主要文件：

- `backend/app/routers/course_feedback.py`
- `backend/app/course_feedback_service.py`
- `backend/app/study_service.py`
- `backend/app/agents/content_workflow.py`

当前 router 调用 `submit_course_feedback_with_rewrite`，内部是两阶段：

1. `submit_course_feedback`：
   - 先将原始反馈写入 `feedback.jsonl`，状态 `pending_analysis`；
   - 调用 Feedback Analyst；
   - 产出问题类型、诊断、示范改写、`ruleCandidate`；
   - 状态变为 `analyzed`；
   - 合并到 `optimization_rules.json`。
2. `generate_rewrite_proposal`：
   - 普通意见调用 Segment Rewriter；
   - 含“删除、删掉、去掉、移除、不需要这段”等意图时，确定性返回空文本候选，不调用模型；
   - 将 proposal 写入反馈的 `rewriteSession.latestProposal` 和 attempts。

正常响应含：

- `feedbackId`；
- `status`；
- `message`；
- `rewriteProposal`（正常预览）；或
- `rewriteError`（反馈已保存但候选生成失败）。

### 2.3 用户确认与课程内容落盘

前端收到 `rewriteProposal` 后显示：

- 被反馈内容；
- 前文、后文；
- 修改前 / 修改后；
- 删除候选显示“这段内容将被删除”；
- “继续修改”；
- “确认替换 / 确认删除”。

确认后调用 `apply_course_feedback_rewrite`：

1. 定位 task 和 study guide；
2. 优先使用结构化 fragment / field / section / item 锚点；
3. 校验原始文本仍存在，避免误改；
4. 只修改目标字段或目标列表项；
5. 重建当前 guide 的 `sections` mirror；
6. 保存 workspace；
7. 将 feedback/session 标为 `accepted`；
8. API 返回权威 workspace，前端直接替换当前 state，立即显示修改效果。

已有测试已覆盖故事版问题项精确删除：`backend/tests/test_course_feedback_replacement.py` 中 `test_story_question_can_be_deleted_by_exact_anchor` 和删除不调用模型的测试。

### 2.4 “整体修改当前小节”是另一条链

`AiCompanion.tsx` 的“整体修改当前小节”不是整门课程全局修改，而是修改当前 task 的四个讲义小节之一。后端生成完整 `revisedSection`，带 `baseRevision`，用户预览后再应用。

当前工作区已有其他未提交改动，为该链增加同一 feedback session 的多轮 refine。后续实施不得覆盖或重复这些用户改动；划词片段链与小节整体链应共享生命周期规则，但保留不同 proposal 结构。

## 3. 反馈数据现在存在哪里、如何提炼

### 3.1 不是堆在 Python 代码里，也不在 SQLite

每门课程存两个文件：

`backend/data/courses/{course_id}/feedback/feedback.jsonl`

- 原始划词或小节意见；
- 上下文与结构锚点；
- 模型分析；
- rewrite session 和 attempts；
- 最新候选；
- 确认结果与错误。

`backend/data/courses/{course_id}/feedback/optimization_rules.json`

- 最多 24 条 rules；
- 最多 40 条 strong directives；
- 最长 5000 字的 summary prompt。

最终课程内容在 `workspace.json`；反馈本身没有 SQLite 表或迁移。

### 3.2 当前提炼方式

单条意见先由模型提炼为：

- `problemTypes`；
- `diagnosis`；
- `suggestedRewrite`；
- 一条可复用 `ruleCandidate`。

规则通过以下简单条件合并：

- title 相同；或
- type 相同且 preferred pattern 完全相同。

命中后追加来源 feedback ID、更新规则并提高 weight；否则新增规则。后续继续生成课程时，`study_service.py` 会把规则摘要和 strong directives 拼入 course prompt。

因此后台**确实有提炼**，不是原始反馈直接塞进代码；但提炼仍较粗糙，没有语义去重、冲突处理、关闭或淘汰机制。

### 3.3 当前已有“减法”

- 输入长度裁剪；
- context 白名单；
- fragments 最多 30；
- rules 最多 24；
- directives 最多 40；
- prompt 最多 5000 字且只取前 12 条 active rule；
- GET 默认只返回最近 50 条；
- 同标题/同 pattern 规则可合并；
- 永久删除整门课程时反馈目录一并删除。

### 3.4 当前没有的“减法”

- `feedback.jsonl` 无总量上限；
- session attempts 无轮数/字符上限；
- pending、failed、放弃预览永久保留；
- 接受后仍保留大体积中间候选；
- 没有关闭、放弃、删除单条反馈 API；
- 没有停用/删除/合并规则的用户入口；
- 每次读写整份 JSONL，且没有反馈文件锁；
- 规则满额时只是截掉末尾，不是按价值淘汰。

更关键的是：当前小节反馈在用户**确认应用之前**就会激活 rule 和 strong directive；即使用户关闭预览，意见仍可能影响后续课程生成。历史 fallback 甚至会从所有 section/global 日志恢复 MUST 指令，没有过滤 accepted 状态。

## 4. 需求理解与目标行为

### 4.1 划词反馈必须是可确认的修改工作流

目标时序：

`选区 → 写意见 → 生成候选 → 明确预览 → 继续修改 / 放弃 / 确认 → 页面立即刷新`

不能再把“原始反馈保存成功”当作整个功能成功。响应应明确区分：

- 反馈是否保存；
- 分析是否完成；
- 修改候选是否生成；
- 是否等待用户确认；
- 是否已经应用。

### 4.2 反馈的两种价值必须分离

一次反馈同时可能有：

1. **当前内容修复价值**：删掉/改写眼前这句话；
2. **未来生成偏好价值**：以后课前准备都不要放这种综合问题。

两者不应绑定成“提交即永久生效”。建议默认：

- 当前内容：用户确认 proposal 后应用；
- 未来偏好：随确认动作一并激活；
- 用户也可单独选择“只改当前内容，不记为以后偏好”；
- 放弃候选则不激活偏好。

### 4.3 “做减法”的目标不是马上删光原始信息

反馈刚提交时仍需保留原始上下文以便定位、诊断和恢复。正确的减法时机是：

- session 结束后；
- 规则已提炼且确认后；
- 候选已应用或明确放弃后；
- 超过保留期限后。

最终长期保留“已确认结论和可复用规则”，删除重复上下文和无用候选。

## 5. 推荐目标数据模型与状态机

### 5.1 第一阶段继续使用课程目录文件

个人本地版数据量目前不要求立即迁 SQLite。先抽出独立的 `course_feedback_store.py`（命名可在实施时确定），集中负责锁、原子 mutation、压缩与兼容读取，避免继续扩大 1100+ 行的 service。

建议 feedback 顶层状态：

- `pending_analysis`：原始意见已安全保存；
- `analysis_failed`：分析失败，但可以重试；
- `awaiting_confirmation`：候选已生成；
- `accepted`：用户确认并应用；
- `abandoned`：用户明确放弃；
- `expired`：旧的开放会话超时归档。

建议 session 状态：

- `open`；
- `accepted`；
- `abandoned`；
- `expired`。

规则状态：

- `proposed`：已提炼但尚未确认；
- `active`：用户确认用于未来生成；
- `inactive`：用户停用；
- `superseded`：已被更准确规则合并替代。

### 5.2 规则只在确认后激活

提交与分析阶段只创建 proposed rule，不进入 prompt。用户确认时可以选择：

- “应用并记住这个偏好”（默认）；
- “只修改这一次”。

放弃时 proposed rule 变为 discarded 或直接从候选集合移除。legacy fallback 必须同步过滤，只允许 accepted/active 来源恢复，不得扫描 pending/abandoned/failed 意见。

### 5.3 Session 瘦身策略

建议默认：

- open session 最多 8 轮；
- 只保留最近 2 个完整候选；更早 attempts 保留 input comment、摘要和 hash；
- accepted 后长期保留：原始意见摘要、最终变更摘要、目标锚点、accepted/applied revision、来源 rule IDs；
- accepted 后移除：重复 before/after/sectionText、旧完整候选、冗长模型 rationale；
- abandoned 后保留最小摘要，立即移除 `latestProposal` 的大对象；
- analysis failed 只保留错误类别和短消息，不长期保留模型完整 payload；
- 可选：30 天无活动的 open session 标为 expired 并瘦身。

### 5.4 规则库减法

不能只做“最多 24 条然后截断”。建议每次激活规则时执行确定性整理：

1. 精确/标准化去重；
2. 同类同方向合并来源与 weight；
3. 同类冲突规则标记为待选择，不能同时进入 prompt；
4. superseded/inactive 不进入 summary；
5. prompt 由 active rules 每次重建，而非累积字符串；
6. 提供轻量“课程偏好”面板：查看、停用、删除、合并来源。

这不是“管理后台”，只是单课程的本地设置面板，符合项目边界。

### 5.5 是否迁 SQLite

暂不作为 P0。只有当反馈数量明显增长、跨文件一致性与查询需求成为持续负担时，再设计：

- feedback_sessions；
- feedback_attempts；
- feedback_rules；
- feedback_rule_sources。

如以后迁移，必须先双读兼容、备份验证和显式离线迁移，不能直接对真实库试跑。

## 6. 分阶段实施计划

## 阶段 A：P0 修复当前“只显示提交成功”

### A1. 统一提交响应契约

后端返回明确字段，例如：

- `feedbackSaved`；
- `analysisStatus`；
- `proposalStatus`；
- `rewriteProposal`；
- `rewriteError`；
- `canRetryProposal`。

失败生成候选时不能返回模糊的整体成功状态。

### A2. 修复前端状态与错误优先级

`SelectionToNoteToolbar` 中：

- 有 proposal → 进入 preview；
- 无 proposal 且有 rewriteError → 进入“反馈已保存，但修改建议生成失败”的**部分成功**状态，直接展示 rewriteError；
- 只有后端明确声明“仅记录、不生成候选”时才显示纯 success；
- 提供“重试生成修改建议”按钮，不重复创建原始 feedback；
- 删除请求预览明确显示“将删除这一个结构化列表项”；
- apply 成功后保留短暂成功态，再用权威 workspace 刷新。

建议把反馈对话框状态 reducer / view 抽到新文件，避免继续扩大 `ModuleView.tsx`；现有 `SelectionToNoteToolbar.tsx` 可保留选区捕获职责。

### A3. 增加运行版本可诊断性

考虑给 API 诊断或响应增加 app build/version（不暴露密钥），并修复/规避中文路径下 reload：

- 开发说明明确“后端代码变更后显式重启”；
- 验收前确认 worker 启动时间晚于代码修改时间；
- 不把 watcher 是否工作建立在猜测上。

这一步能避免“源码已修但当前 8000 仍是旧代码”的假修复。

### A4. 恢复最新这条反馈

不直接脚本修改真实数据。代码上线并重启后，用户对该句重新发起删除反馈即可正常生成删除预览。若用户希望保留原反馈 ID，再单独提供“重试候选”接口，由后端从已保存 feedback 安全重建 proposal；禁止手工改 `feedback.jsonl`。

## 阶段 B：P0 生命周期与一致性

### B1. 抽离反馈存储层并加课程级锁

- 新建反馈 storage 模块；
- 提供锁内 `mutate_feedback_entries` / `mutate_rules_store`；
- read-modify-write 必须在同一课程锁内；
- 保留临时文件 + `os.replace` 原子写；
- service 不再散落全文件读写。

### B2. 增加 close/abandon 与 retry API

建议：

- `POST .../course-feedback/{feedback_id}/abandon`；
- `POST .../course-feedback/{feedback_id}/proposal/retry`；
- 可选 `GET .../course-feedback/open` 用于刷新恢复未结束会话。

前端关闭预览、“取消替换”、开始新对话、切换 task/section 时，需要明确产品语义：

- 普通关闭可提示“保留草稿 / 放弃”；
- 明确放弃才调用 abandon；
- 页面刷新可恢复 open session，避免候选凭空消失。

### B3. 规则确认制

- 分析时写 proposed rule；
- apply 时按用户选项激活；
- abandon/failed 不进入 prompt；
- 修复历史 directive fallback 状态过滤；
- 对无状态旧记录制定一次性兼容：有 accepted rewrite 的视为 accepted，其余不自动升级成 MUST，并在规则页提示用户确认。

### B4. Workspace 并发保护与幂等

当前 apply 是 load → 改内存 → save，保存时未传 `expected_revision`。应：

- load 时记录 workspace revision；
- save 时传 expected revision，冲突返回 HTTP 409；或提供锁内 mutate API；
- apply 以服务端 `latestProposal` 为权威，不再信任客户端传回的 original/rewritten/target；
- accepted session 重复 apply 返回上次成功结果，做到幂等；
- feedback 不存在/类型不匹配/状态不允许分别返回清晰错误。

## 阶段 C：P1 数据做减法与课程偏好 UI

### C1. Attempts 与 payload 限额

- 每 session 最大轮数；
- 总评论字符预算；
- 保存最近 N 个完整候选；
- 超限后提示开始新 session，不无限拼接 conversation；
- global attempt 使用适合小节 proposal 的 schema，不再只存空 `rewrittenText`。

### C2. 会话结束压缩

- accepted/abandoned 时执行确定性 compact；
- compact 前后保留可验证 hash 和最终摘要；
- 新增显式 maintenance endpoint 或在课程打开时做轻量惰性整理；
- 第一版不做后台定时线程，保持个人本地应用简单。

### C3. 课程偏好面板

在课程设置中增加轻量组件，展示：

- active/proposed/inactive 规则；
- 规则摘要、适用范围、来源反馈数量；
- 停用、删除、合并；
- “只影响后续生成，不会自动重写已生成课程”的说明。

无需管理员角色或管理后台。

## 阶段 D：P2 可选 SQLite 迁移

仅在文件方案证明不足时执行。需另立迁移方案并再次确认，不与本轮 P0/P1 混为一个提交。

## 7. 影响范围

预计实施会涉及：

### 后端

## 8. 风险与兼容性

1. **用户未提交改动冲突**：当前全局小节多轮反馈、答案一致性等改动尚在工作区。实施前重新看 `git diff`，按职责拆分，不覆盖现有改动。
2. **旧数据状态不完整**：不能把所有历史 section feedback 自动视为 active MUST；应按 accepted evidence 迁移，其余待确认。
3. **错误删除风险**：只允许服务端保存的结构锚点和原文校验通过后删除；保留 stale 检查，禁止宽泛递归 fallback 误删首个同文内容。
4. **并发覆盖学习进度**：必须使用 expected revision / 锁内 mutation。
5. **跨文件半成功**：文件存储没有数据库事务。先通过幂等操作、状态重算和写入顺序降低风险；必要时增加小型 transaction journal，而不是假装原子。
6. **模型延迟**：划词首次提交当前可能串行做分析和改写两次模型调用。删除应保持确定性零额外模型；普通改写可研究一次调用返回分析+候选，或先返回可轮询 job，但不在 P0 里贸然改大架构。
7. **页面刷新丢预览**：加入 open session 查询后恢复；恢复前不应自动 abandon。
8. **Prompt 污染**：未确认、失败、放弃规则不得注入；冲突规则不能同时成为 MUST。

## 10. 人工验收清单

必须在**显式重启后端**后，使用真实后端而非 demo：

1. 打开故事版课程课前准备；
2. 划选一个 `storySection.questions` 列表项；
3. 输入“这道问题多余，请删除”；
4. 应看到：
   - 反馈已保存；
   - 修改前为原问题；
   - 修改后为“这段内容将被删除”；
   - “确认删除”按钮；
5. 未确认前刷新课程，原内容仍在，规则不应进入 active prompt；
6. 恢复 open session 或重新打开预览；
7. 确认删除后，该问题立即从当前页面消失，其他课前准备内容和其他三小节不变；
8. 刷新页面后删除结果仍在；
9. 反馈记录为 accepted；
10. 选择“记住偏好”时规则 active；选择“只改本次”时规则不 active；
11. 再测试一次普通改写、多轮 refine、放弃和网络/模型失败；
12. 验证后端 worker 启动时间晚于本次代码修改时间。

## 11. 建议提交拆分

由用户本人提交，AI 不执行 git commit。建议至少拆成：

1. `fix(feedback): 修复划词反馈部分成功与删除预览链路`
2. `refactor(feedback): 抽离带锁反馈存储与状态机`
3. `feat(feedback): 增加重试放弃和确认后规则激活`
4. `feat(feedback): 增加会话压缩与课程偏好维护`
5. `test(feedback): 补持久化并发和前端状态测试`

每类改动独立验证，避免再次形成大杂烩。

## 12. 需要用户确认的产品决策

建议采用以下默认值，确认后实施：

1. **规则激活**：只有确认应用后才生效；确认时默认勾选“记住这个偏好”。
2. **取消/关闭**：关闭预览先保留草稿；明确点“放弃”才关闭后端 session。
3. **历史保留**：accepted 长期保留精简摘要；abandoned/failed 保留精简摘要，删除完整候选。
4. **多轮上限**：每个反馈 session 最多 8 轮，超限后开始新会话。
5. **迁 SQLite**：本轮不迁；先完成文件存储锁、状态机与压缩。
6. **旧反馈规则**：已有 accepted 记录继续 active；未确认/无 accepted 证据的旧记录改为 proposed，等待用户在课程偏好页确认。

如以上决策可行，下一步按阶段 A → B 实施；阶段 C 可在核心链路验收后另行确认范围。
