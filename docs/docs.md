# docs 文档库总规则（宪法）

> 本文件是 `docs/` 的最高规则，所有文档工作遵循此处约定，优先级仅次于根目录 `CLAUDE.md`。
> 结构变更（增删目录、改命名规则、改生命周期）必须先改本文件，再动目录。
> 人是所有"设计裁决"的唯一所有者；AI 负责起草、加工、同步与记录，不拥有裁决权。

---

## 1. 文档库定位与结构

本库是期末粥++ 的**人机协作开发框架**，服务于两件事：稳定迭代项目（project）、
人借项目学习（study）。

```
docs/
├─ docs.md          ← 本文件（总规则/宪法）
├─ project/         ══ 开发文档库 ══
│  ├─ project.md    ← 开发库总文档（全局架构参考 + 域地图）
│  ├─ DEV_BOARD.md  ← 实时看板（状态真源，会话结束时刷新）
│  ├─ log/          ← 开发日志（AI 记录，一天一文件，append-only）
│  ├─ bugs/         ← 错误档案库（全量持久，AI 遇错自动建档）
│  ├─ ideas/        ← 新功能灵感池（用户随手记，只进不改）
│  ├─ proposals/    ← 变更提案（优化/新功能/系统级变更的完整方案）
│  │  └─ archive/   ← 已落地提案归档（只进不改）
│  ├─ draft/        ← 测试草稿与实验性文件（course-style-lab 等，不保证维护质量）
│  ├─ modules/      ← 可见功能域（一域一文件夹，前后端纵切）
│  └─ core/         ← 引擎与基础设施域（用户不可见）
└─ study/           ══ 学习文档库 ══
   ├─ study.md      ← 学习库总文档
   ├─ guide/        ← 学习指导（方法论、路线图，AI 编写）
   ├─ patterns/     ← 概念→项目实例对照库（理论↔本项目代码）
   └─ log/          ← 学习笔记（用户执笔为主，AI 可协同整理）
```

**域清单**（20 个 modules + 9 个 core，详见 project.md 域地图）。

## 2. 核心机制：三个文档层级 + 两条回流

### 2.1 三个文档层级

| 层级 | 载体 | 回答的问题 | 维护者 |
|---|---|---|---|
| 意图层 motivation | 根 `CLAUDE.md` + 各域 `design.md` | 为什么做、要什么、不许什么 | 人裁决 |
| 设计层 design/specs | 各域 `design.md` + `designs-specs.md` | 模块边界、契约、不变量 | AI 起草，人审 |
| 记录层 log/board | `log/` + `DEV_BOARD.md` | 现在做什么、那天发生了什么 | AI 记录 |

### 2.2 两条回流（缺了框架就死）

1. **实现 → 设计**：实现中发现 design/specs 与现实不符，**不许悄悄改文档迁就代码，也不许悄悄改代码迁就文档**。
   在该域 `designs-specs.md` 的「设计异议」节记录，交人裁决：改文档、改代码、或记为已知债务。
2. **提案 → 设计（落地收尾）**：`proposals/` 落地后，**必须**把耐久结论合并回对应域的 design.md，
   提案移入 `archive/`。这一步没做完，任务不算完成。

### 2.3 双文档模式（每个域文件夹内固定两件套）

| 文档 | 内容 | 模式一：已有模块（考古） | 模式二：新功能（规划） |
|---|---|---|---|
| `design.md` | 定位/关键决策与理由/不变量/禁区/设计异议。契约性内容。 | AI 从代码+git史逆向起草 → 人审定 | 源自 proposal |
| `designs-specs.md` | 文件清单/入口与调用链/数据契约/测试锚点/导读。事实性"是什么"。 | 从代码生成，随代码同步 | 先写 specs 指导实现，落地后随代码同步 |

**导读**（specs 的第一节）服务人的学习：本域管什么、一条典型调用链、常见困惑。

**冲突处理**：specs 与代码冲突 → 以代码为准并更新 specs；design 与代码冲突 → 设计异议，回流人裁决。

## 4. 生命周期规则

### 4.1 灵感 → 提案 → 落地 → 沉淀

```
ideas/（一句话即可，只进不改，用户专属）
  ↓ 用户决定要做时，要求 AI 研究并起草
proposals/<提案名>.md（现状分析/需求理解/影响范围/实施步骤/风险与兼容性/测试验收——即 CLAUDE.md 要求的方案文档）
  ↓ 用户确认后实施（实施过程记录进 log/）
落地 → 耐久结论合并回域 design.md → 提案移入 proposals/archive/
```

### 4.2 log 规则（append-only 流水）

- 文件名 `YYYY-MM-DD.md`，跨会话同日追加，二级标题分隔会话。
- **AI 在每个有实质工作的会话结束时必须写当日 log**（与更新看板同级义务）。
- 记什么：做了什么/关键决策及理由/发现的问题/设计异议/下一步。不记流水账。
- 写完不改；写错在当日或次日文末勘误，不删原文。

### 4.3 bugs 规则（错误档案库）

- **AI 遇错自动建档义务**：任何会话中遇到（或被告知）真实错误——运行失败、测试红灯、
  行为异常、构建崩溃——必须在 `bugs/` 建档（命名 `YYYY-MM-DD-<英文slug>.md`，
  模板见 bugs.md），无论当时是否顺手修复。
- **与看板 🐛 区分工**：bugs/ 是全量持久档案（不删）；看板只保留活跃/待验证条目做状态跟踪。
- 状态流转：🔴 待修复 → 🟡 已修待验证 → ✅ 已关闭（附 commit）；⚪ 暂不修（附理由）。
- 误报/根因纠正：原档案标注更正并保留原文，不删文件。

### 4.4 会话义务（每个 AI 会话的标准动作）

1. 开始：读 `docs/project/DEV_BOARD.md` → `git status --short`
2. 动手前：涉及某域时先读该域 design.md + designs-specs.md（已有时）
3. 结束：更新看板 + 写当日 log（有实质工作时）+ 验证三件套（有代码改动时）
4. 大变更仍走 CLAUDE.md 的"先方案后实施"铁律（方案 = proposals/ 里的文档）

## 6. AI 生成语言规范（用户执笔，AI 只读遵守）

> 本节是文档库的**文风宪法**：约束 AI 在写作与交互中的表达方式。
> 条目由用户手动编写存入——这里是规范的用户专区（如同 ideas/ 之于灵感）；
> AI **不得改写、删除、替用户预填**任何条目，发现规范缺失也不许自行起草塞入，
> 只能提醒用户可自行补充。若 AI 认为某条规范需要调整，在会话中口头提议，由用户决定。
>
> **适用范围**：docs/ 库内全部 AI 产出（design.md / designs-specs.md / log / 看板 /
> proposals / bugs / study 侧文档）以及 AI 与用户围绕文档工作的日常交互表达。
> AI 在每次开始文档工作前应回读本节；与本文件其他节冲突时，本节优先。

## 8. 学习库（study/）规则

学习材料按用途分流，三类文档互相链接但不重复全文：

| 位置 | 记录什么 | 默认作者与边界 |
|---|---|---|
| `guide/` | 学习路线、课次安排、阅读导航、代码锚点、练习、阶段进度 | AI 可起草维护，人使用与裁决；不把用户心得冒充结论 |
| `patterns/` | 一个真实遇到的 Python/Web/全栈概念及其本项目实例 | AI 起草，人阅读确认；不从教材目录批量生成 |
| `log/` | 用户自己的复述、心得、困惑、错误猜测、想通之处和下一步 | 用户执笔为主；AI 只有经用户明确授权才能协助整理，并标注“AI 协助整理/待用户确认” |

材料分流：路线推进→`guide/`，概念抽象→`patterns/`，个人理解→`log/`。

`guide/项目学习指南.md` 是稳定路线图；`guide/学习路线记录.md` 记录实际推进过程。
`patterns/` 一篇一个概念，至少包括：概念通俗与严谨解释、本项目文件/函数/调用链/字段、采用理由、观察练习、常见误解与边界、学习状态。状态区分“待阅读、已阅读待复述、已过关”；“已过关”必须以用户复述或明确确认为依据。
`log/` 继续采用 `YYYY-MM-DD.md`、append-only；AI 不将自己的讲解冒充用户心得。

**学习成果回流**：用户确认过的 patterns 或 log 理解，可被 AI 引用进对应域 `designs-specs.md` 的“导读”；学习过程本身不自动视为域设计结论。
