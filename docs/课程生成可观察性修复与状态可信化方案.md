# 课程生成可观察性修复与状态可信化方案

> 状态：待用户确认，未开始业务代码修改  
> 编写日期：2026-08-28  
> 目标范围：课程复习主线后台生成的任务恢复、轮询可靠性、阶段可见性与重试语义  
> 不在本方案范围：降低课程质量标准、恢复低质量兜底、调整模型总超时、并行启动多个 worker、课程生成效率瘦身

## 1. 背景与问题定义

当前一节课通常需要串行完成讲义生成和自测生成，正常为 2 次逻辑模型调用；讲义或自测触发硬校验修复时最多为 4 次。真实任务可能持续数分钟到十几分钟，因此“长时间运行”本身不一定异常。真正影响体验的是：用户无法可靠判断任务是否仍在运行、当前运行到哪里、是否正在恢复，以及界面上的失败是否为真实后台失败。

本方案优先修复四个已确认问题：

1. 刷新页面后，React 内存中的 Job 丢失，无法恢复后台任务。
2. 一次临时轮询或 workspace 请求失败，会被前端伪造成 Job 失败并停止轮询。
3. Job 已返回任务级 modelUsage，但前端使用全局用量，且当前后端阶段粒度还不足以区分讲义、自测和修复。
4. 前端临时构造 maxAttempts=2，后端实际课程 Job 为 max_attempts=1；Job 尝试、模型传输重试、主备切换和内容修复被混为一谈。

### 1.1 成功标准

完成本方案后，用户应能明确回答：

- 后台任务现在是排队、运行、停止请求中、完成、真实失败，还是仅状态同步中断？
- 页面刷新后，原任务是否仍能自动恢复并继续显示？
- 当前是在生成讲义、修复讲义、生成自测、修复自测，还是保存结果？
- 当前是哪一节课、使用哪个模型、当前调用持续多久？
- Job 尝试次数是多少；内容修复次数是多少；是否发生模型请求失败或备用模型切换？
- 最近一次后台心跳或前端同步是什么时间，任务是“慢但仍活着”还是“长时间无进展”？

本方案不展示未经校准的“成功概率百分比”。

## 2. 当前实现与根因分析

## 2.1 前端 Job 只存在内存中

- 状态定义：`web/src/App.tsx:139-144`
- 实例状态：`web/src/App.tsx:574`
- 只有用户入队后才创建本地状态：`web/src/App.tsx:1570-1590`
- 后端已有活动任务恢复接口：`backend/app/routers/strategy.py:124-130`
- 底层查询：`backend/app/agent_runtime.py:440-449`

根因不是后端缺少接口，而是前端 API 和课程加载生命周期没有接入该接口。

## 2.2 通信错误和领域失败共用同一个 failed 状态

`web/src/App.tsx:605-650` 使用固定 1.8 秒 setInterval：

1. GET Job；
2. Job running 时 GET workspace；
3. 任意步骤抛错后，把本地 Job 的 status 改为 failed；
4. effect 因 Job 不再是 queued/running 而停止轮询。

这破坏了“服务端 Job 状态是唯一事实源”的原则。网络异常只能说明本次同步失败，不能说明后台生成失败。

此外，固定 setInterval 不等待上一轮完成；当网络请求超过 1.8 秒时可能出现重叠轮询、响应乱序和额外负载。

## 2.3 现有 modelUsage 可用但粒度仍不够

`backend/app/model_usage.py:16-117` 已记录：

- calls / failures / token 用量；
- currentCall.model / startedAt / stage / taskId / attempt；
- stages 聚合；
- recent 调用记录。

`backend/app/agent_runtime.py:490-507` 已将 scoped modelUsage 放入 AgentJob。

但是当前还有两个缺口：

1. 前端状态卡在 `web/src/components/ModuleView.tsx:1050-1072` 额外轮询全局 `/model-usage`，可能混入其他任务或历史用量。
2. 后端课程生成当前在 `content_workflow` 中以统一的 `lesson` stage 包裹 LessonBuilder，taskId 也未按每节传入，因此仅靠现状还不能可靠区分“讲义/自测/修复”。

因此实施时不能只改 UI 文案，必须先补齐任务级阶段契约。

## 2.4 重试语义混乱

- 前端本地临时 Job：`maxAttempts: 2`，见 `web/src/App.tsx:1578-1585`。
- 后端课程生成 Job：`max_attempts=1`，见 `backend/app/routers/strategy.py:140-154`。

需要明确区分四层概念：

| 层级 | 含义 | 当前行为 | UI 展示原则 |
|---|---|---|---|
| Job attempt | 整个后台处理器执行次数 | 课程生成 1 次 | 显示“任务执行 1/1” |
| Provider transport retry | 同一模型连接/HTTP 重试 | 内部自动进行 | 不冒充 Job attempt；仅显示“模型连接恢复中”或失败次数 |
| Provider failover | 主模型不可用后切备用 | 自动进行 | 由当前/最近模型变化与失败记录展示 |
| Content repair | 讲义或自测硬校验后的第二次生成 | 各最多 1 次修复 | 显示“修复讲义（第2次）”或“补正自测（第2次）” |

## 2.5 时间字段的实际含义

- AgentJob.createdAt：入队时间。
- AgentJob.updatedAt：claim、60 秒 lease 心跳、完成、失败或取消时更新，可作为后台存活信号，但不等同于内容进度。
- modelUsage.currentCall.startedAt：当前模型调用开始时间。
- modelUsage.updatedAt：模型调用完成/失败时间；当前调用开始时现实现不会更新该字段。
- 前端 startedAtMs：当前来自浏览器点击时间，刷新后丢失。

方案中必须分别展示“排队时间”“总运行时间”“当前阶段时间”“最近后台心跳”“最近同步时间”，不能混用。

## 3. 需求与交互设计

## 3.1 服务端状态是唯一事实源

前端不得自行把服务端 Job 改为 failed，也不得猜测 maxAttempts。所有 queued/running/completed/failed/cancelled 状态均来自 GET Job 或 active-job。

前端只维护额外的“客户端同步状态”：

`syncing | healthy | degraded | offline`

建议状态模型：

`StrategyGenerationSession`

- courseId
- job: AgentJob | null
- source: submitted | recovered
- syncStatus: syncing | healthy | degraded | offline
- consecutiveSyncFailures
- lastSyncedAt
- syncError
- stopRequested（仅用于“正在请求停止”的前端过渡）

注意：`syncStatus=degraded/offline` 时，必须保留最后一次可信的 Job 状态，不可改写成 failed。

## 3.2 页面刷新和课程切换后的恢复

恢复时机：

1. 用户登录态和课程列表加载完成后；
2. activeCourseId 确定或切换时；
3. 当前内存中没有该课程的活动 Job 时。

调用：

`GET /courses/{courseId}/strategy-documents/active-job`

处理：

- 返回 queued/running Job：恢复 session，`source=recovered`，以 Job.createdAt 计算总耗时并启动轮询。
- 返回 null：不创建活动 session。
- 请求失败：显示“生成状态暂时无法同步”，但不能声称后台失败；按退避策略重试。
- 当前已有相同 Job：只更新，不重置计时或 UI。

为避免切换课程时丢失其他课程的运行任务，本阶段保持全局只展示当前追踪的课程 Job，但每次进入课程都重新查询该课程 active-job。单 worker 模型下足够满足本地版需求；不扩建多任务管理中心。

## 3.3 入队响应必须可信

建议后端在保持兼容的前提下，把 approve-job 响应从：

`{ jobId, courseId }`

扩展为：

`{ jobId, courseId, job }`

其中 job 直接来自 `get_agent_job(job_id)`，包含真实 `maxAttempts=1`。

前端优先使用响应中的完整 job，不再手工构造 attempts、maxAttempts、createdAt 和 updatedAt。保留 jobId/courseId 字段，避免破坏 demo 或其他调用方。

若暂不修改响应，也可以入队后立即 GET Job；但扩展响应能少一次竞态窗口和请求，因此作为推荐方案。

## 3.4 可靠轮询策略

用自调度 setTimeout 或独立 hook 替代固定 setInterval，保证单飞：上一轮完全结束后才安排下一轮。

建议节奏：

- 正常 queued/running：2 秒；
- 连续失败 1 次：2 秒后重试；
- 连续失败 2 次：4 秒；
- 连续失败 3 次及以上：8 秒，最大 15 秒；
- 任意成功同步后清零失败次数并恢复 2 秒。

每轮分两步，错误隔离：

1. GET Job 是主状态同步；成功后立即保存 Job。
2. 仅当 Job.updatedAt、modelUsage.updatedAt、currentCall 或终态发生变化时，再 GET workspace；workspace 请求失败只标记“内容预览刷新失败”，不影响 Job 的可信状态。

终态处理：

- completed：刷新 workspace，保留本批摘要，不在 8 秒后自动清空。
- failed：显示后端原始 error 和分类建议，留在计划状态卡，不强制跳资料页。
- cancelled：刷新 workspace，说明已完成的小节已保留。

需要防止旧请求覆盖新 Job：每次写状态前校验 jobId，并在 effect 清理时使用 AbortController 或 generation token。

## 3.5 阶段契约

建议采用稳定的机器字段，而不是让前端解析中文日志。

### 第一阶段必要 stage

| stage | 用户文案 | taskId | attempt 含义 |
|---|---|---|---|
| preparing | 正在读取课程资料 | 可空 | 无模型调用 |
| lesson_guide | 正在生成本节讲义 | 必填 | 1=首次，2=硬校验修复 |
| lesson_questions | 正在生成本节自测 | 必填 | 1=首次，2=覆盖/结构修复 |
| finalizing | 正在校验并保存本批课程 | 可空 | 无模型调用 |

当前 modelUsage 只围绕模型调用，无法表达 preparing/finalizing。为避免本次引入复杂事件系统，建议：

- 模型调用中的阶段由 modelUsage.currentCall/stages/recent 提供；
- 非模型阶段由一个轻量、持久化的 Job progress 字段提供。

### 推荐新增 Job progress

在 agent_jobs 增加 `progress_json TEXT NOT NULL DEFAULT '{}'`，并在 `get_agent_job` 返回：

- stage
- taskId
- stageAttempt
- message（可选，调试用，不作为前端逻辑依据）
- updatedAt

新增一个受 lease_token fencing 保护的 `update_agent_job_progress`：只有当前运行代可以更新，避免旧线程覆盖新代状态。

更新点：

1. handler 开始：preparing；
2. 讲义第一次/第二次调用前：lesson_guide + attempt；
3. 自测第一次/第二次调用前：lesson_questions + attempt；
4. 一节成功发布后：finalizing 或下一课阶段；
5. 返回前：finalizing。

为什么推荐持久化 progress，而不是只扩展内存 modelUsage：

- 页面刷新可恢复；
- backend 进程重启后仍保留最后阶段；
- 模型尚未开始或已经结束、正在保存时也有明确阶段；
- Job 状态与 progress 同属服务端事实源。

兼容策略：progress 缺失或为空时，前端回退到 modelUsage.currentCall；仍无数据时显示“后台处理中”，不能报错。

### modelUsage 阶段细化

同时把 LessonBuilder 的调用上下文从统一 `lesson` 拆为：

- `lesson_guide` + 当前 taskId；
- `lesson_questions` + 当前 taskId。

第二次修复不需要新增动态 stage 名，使用 currentCall.attempt 或 progress.stageAttempt=2 表达，避免 stages 聚合被无限拆散。

provider failover 不新增 Job stage。UI 根据 currentCall.model 和 recent 中 failed/model 变化显示“模型连接失败，已尝试恢复/切换模型”。不承诺精确剩余连接重试次数，除非后端未来显式暴露 provider attempt budget。

## 3.6 状态卡展示

为遵守 `ModuleView.tsx` 大文件约束，新建独立组件：

`web/src/components/CourseGenerationStatusCard.tsx`

并将阶段映射与时间/健康度纯逻辑放到：

`web/src/features/courseGeneration/generationStatus.ts`

状态卡建议分三层：

### 第一层：一句话结论

- 等待后台 worker 接手
- 正在生成《课程标题》中的“第 N 课：xxx”讲义
- 讲义校验发现缺项，正在第 2 次修复
- 讲义已完成，正在生成本节自测
- 正在保存本批课程
- 状态同步暂时中断，后台最后状态仍为运行中
- 真实生成失败

### 第二层：可验证信息

- 已完成课程：x/y；
- 排队/运行总耗时；
- 当前阶段耗时；
- 最近后台心跳；
- 最近前端成功同步；
- 当前模型；
- Job 执行：1/1；
- 模型调用：成功 x、失败 y；
- token 用量。

### 第三层：操作

- 刷新状态：同时 GET Job 和 workspace；
- 请求停止：按钮后显示“已提交停止请求，当前模型调用可能需要结束后才能完全停止”；
- 真实失败：按错误分类显示“检查模型配置/检查余额/重试当前课/复制错误详情”；
- 同步中断：显示“重新连接”，不显示“重试生成”。

## 3.7 健康度规则

不显示成功率，采用解释性健康度：

- queued：排队中；
- running 且 Job.updatedAt 距当前小于 90 秒：后台心跳正常；
- currentCall 存在：模型正在处理，并显示调用时长；
- 90～180 秒无 Job.updatedAt 更新：最近心跳延迟，显示黄色提示；
- 超过 180 秒：状态可能异常，建议手动刷新，但仍不得改写 Job failed；
- sync 连续失败 1～2 次：同步波动；
- sync 连续失败 >=3 次：状态同步中断；
- 只有服务端 status=failed 才显示真实失败。

阈值基于当前 60 秒 lease 心跳设计，并应集中定义，不能散落在 JSX 中。

3. 观察讲义→讲义修复→自测→自测修复→保存的阶段变化。
4. 记录不同模型和风格的实际阶段耗时，为未来 ETA 提供分位数基础。

课程效率瘦身（局部修复、合并调用、小模型出题）另立方案，不与本次可观察性修复混在同一改动中。

## 6. 风险与控制措施

### 6.1 progress 与 modelUsage 短暂不一致

可能出现 progress 已切到 lesson_questions，但 modelUsage 仍保留上一调用的 recent。前端优先级：

1. 服务端 Job status；
2. progress.stage；
3. currentCall 作为当前模型细节；
4. recent 只作为历史记录。

### 6.2 后端重启后的状态

progress 持久化后可显示最后阶段；内存 modelUsage 会丢失。UI 应显示“后端重启后正在恢复任务状态”，不能把缺少 modelUsage 当失败。lease 回收和 attempts 上限问题属于相邻稳定性风险，建议在阶段 A 测试中确认，但若需改变队列重领语义，应单独修复并单独验收。

### 6.3 协作式取消

后端当前不能强杀正在进行的单次模型请求。UI 只能准确表达“停止请求已登记，模型调用返回后停止”，不得承诺立即停止。真正的可中断 HTTP 流属于后续模型客户端改造。

### 6.4 工作区现有未提交修改

当前工作区已有用户改动，涉及 App.tsx、api.ts、ModuleView.tsx 等潜在重叠文件。正式实施前必须重新检查 diff，逐处保留用户改动，不能覆盖；若冲突较大，优先先完成新增 hook/组件/纯函数，再做最小接线。

### 6.5 大文件风险

App.tsx 与 ModuleView.tsx 只做接线和删除旧逻辑；核心状态机、轮询和 UI 放新文件。禁止在 ModuleView.tsx 新增顶层组件。

### 6.6 过度轮询

Job 轮询保持约 2 秒以维持实时感；workspace 仅在阶段、更新时间或终态变化时刷新，避免每轮都加载完整 workspace。连续通信失败时退避到最多 15 秒。

## 7. 测试计划

## 7.1 后端自动测试

新增或扩展 pytest：

1. approve-job 返回真实 job，maxAttempts=1。
2. active-job 对 queued/running 返回完整 Job，对终态返回 null。
3. progress_json 对旧数据库自动补列，默认空对象。
4. progress 更新要求正确 lease_token；旧代 token 不得覆盖。
5. lesson guide 第一次、修复、questions 第一次、修复分别产生正确 stage/taskId/stageAttempt。
6. get_agent_job 返回完整 modelUsage/progress，字段为空时兼容。
7. 取消、失败、完成后 progress 保留用于摘要。

后端代码改动后运行：

`cd backend; .\.venv\Scripts\python.exe -m pytest tests -q`

## 7.2 前端验证

当前前端无项目级测试基础，本方案不在同一改动中引入完整 Vitest 基建，以避免扩大范围。至少执行：

- `cd web; npx tsc -b`
- `cd web; npm run build`

如实施时已有 Vitest 基建，则为 generationStatus 纯函数和 hook 增加测试；否则通过可注入 fetch/计时器的结构为后续测试预留边界。

## 7.3 手工验收矩阵

| 场景 | 操作 | 预期 |
|---|---|---|
| 刷新恢复 | running 时 F5 | 同一 jobId 恢复，耗时不归零 |
| 切走再回来 | 生成时切其他模块/课程后返回 | 查询 active-job 并恢复 |
| 单次 Job 请求失败 | 模拟一次 500/断网 | 显示同步波动，保留 running，不停止轮询 |
| workspace 请求失败 | Job 查询成功、workspace 失败 | Job 状态仍可信，仅预览刷新告警 |
| 连续断网 | 断网超过 3 轮 | 显示同步中断和最后同步时间，不能显示真实失败 |
| 恢复网络 | 重新联网 | 自动恢复 healthy，无需重新生成 |
| 讲义正常 | 启动一课 | 显示当前课和“生成讲义” |
| 讲义修复 | 触发硬校验修复 | 显示“修复讲义，第2次” |
| 自测阶段 | 讲义完成后 | 切换到“生成自测” |
| 真实失败 | 主备模型均不可用 | 仅服务端 failed 后显示失败和原始原因 |
| 协作取消 | 模型调用中点击停止 | 先显示停止请求，提示不会立即强杀；已完成课保留 |
| 完成摘要 | 一课完成 | 摘要持续显示，不在 8 秒后消失 |
| 重试信息 | 任意运行任务 | Job 显示 1/1，内容修复和模型失败单独展示 |

## 7.4 完成定义

只有满足以下条件才算本方案完成：

- 刷新可恢复活动任务；
- 临时通信错误不会改写 Job 为 failed；
- 阶段至少可区分讲义、自测、修复和保存，并带 taskId；
- maxAttempts 来自后端真实 Job；
- 全局 model-usage 不再用于课程任务状态卡；
- 终态摘要保留，真实失败和同步失败明确区分；
- 后端全量 pytest、前端 tsc、前端 build 均按项目约束执行并记录结果；
- 真实上游至少完成一次增量单课验收；
- 不降低内容硬校验，不引入低质量兜底，不增加 worker 并发。

## 8. 建议决策

建议批准按 A→B→C→D 分阶段实施，优先完成“状态可信”而不是先做花哨 ETA：

1. 服务端持久化最小阶段进度；
2. 前端恢复 active-job 并分离同步错误；
3. 展示任务级阶段和真实重试语义；
4. 用真实任务验收并积累耗时数据。

需要用户确认的关键选择：

- 是否同意为 agent_jobs 增加兼容的 progress_json 字段，以保证刷新和后端重启后的阶段可恢复（本方案推荐“同意”）。
- 是否同意完成/失败摘要持续保留到下一次生成或用户主动关闭，而不是 8 秒自动消失（本方案推荐“同意”）。
- 是否同意本轮只解决可观察性，不同时修改课程 prompt、硬校验和模型调用次数（本方案推荐“同意”，效率优化另立方案）。
