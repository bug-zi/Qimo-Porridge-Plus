# 进程状态转换｜讲解

刚才我们拿打印任务举了个例子。刚接触三态模型时，你可能还分不清“等 CPU”和“等打印机”。先抓住一条最基本的关系就行：**运行态表示正在占用 CPU；就绪态表示能运行、只差 CPU；阻塞态表示仍缺少某个等待条件。** 三态转换的依据，就是进程是否占有 CPU、是否具备运行条件发生了变化。

## 怎样用两个问题分清三种状态？

先问：进程是否正在占用 CPU？如果正在执行，它处于运行态。

如果没有占用 CPU，再问：现在给它 CPU，它能否立刻继续执行？能够立刻执行的是就绪态；仍要等待 I/O 完成、资源可用或消息到达等事件的是阻塞态。

因此，“没有占用 CPU”不能单独决定状态。就绪态和阻塞态都不占 CPU，区别在于是否已经具备运行条件。这个区别也决定了进程离开运行态后会走向哪里。

## 运行进程离开 CPU 后，为什么会有两条路？

正在运行的进程离开 CPU 时，要看它还能不能继续执行。

- **运行态 → 就绪态**：进程失去 CPU，但仍具备运行条件。典型触发是时间片用完或被更高优先级进程抢占。它回到就绪队列，等待再次调度。
- **运行态 → 阻塞态**：进程执行到必须等待的事件，暂时无法继续。典型触发是请求 I/O 后等待完成，或者申请的资源暂不可用。

打印进程 P 的时间片用完时，任务仍可继续，所以 P 进入就绪态；P 申请打印机而打印机暂不可用时，即使 CPU 空闲也无法继续，所以 P 进入阻塞态。判断这两条转换时，关键问题是“进程是否仍具备运行条件”。

## 阻塞原因解除后，进程为什么先进入就绪态？

当 I/O 完成或所需资源可用时，阻塞原因解除，进程从不能运行变为可以运行，于是发生：

**阻塞态 → 就绪态：等待事件完成，进程被唤醒。**

事件完成只改变进程的可运行性；进程是否占用 CPU 还要看调度结果。打印机可用后，P 已经能继续，但 CPU 可能正由其他进程占用，因此 P 通常先进入就绪队列。

这也解释了为什么阻塞态通常不能直接转换到运行态：中间还缺少“被调度并获得 CPU”这个条件。

## 就绪进程怎样真正开始运行？

就绪队列中的进程都具备运行条件。调度程序从中选中某个进程并把 CPU 分配给它，于是发生：

**就绪态 → 运行态：被调度并获得 CPU。**

“等待调度”属于就绪态，因为进程只差 CPU；“等待 I/O 或资源”属于阻塞态，因为给它 CPU 也不能立即继续。看到“选中”“分配处理机”“获得 CPU”等信息，可以判断为就绪态到运行态。

## 四条直接转换怎样连成一张图？

基础三态模型中的四条常见直接转换是：

```text
就绪态 ──被调度、获得 CPU──→ 运行态
运行态 ──时间片用完或被抢占──→ 就绪态
运行态 ──等待 I/O、资源等事件──→ 阻塞态
阻塞态 ──等待事件完成、被唤醒──→ 就绪态
```

画图时，状态名和触发事件要同时写清。箭头表达状态变化，箭头旁的事件说明变化为什么发生。

## 哪两条转换通常不能直接发生？

**阻塞态通常不能直接到运行态。** 等待事件完成后，进程只是重新具备运行条件；它通常先进入就绪态，随后被调度才进入运行态。若题干明确补充“立即被调度并获得 CPU”，应按题干描述分步判断。

**就绪态通常不能直接到阻塞态。** 就绪进程没有占用 CPU，通常不能执行请求 I/O、申请资源或等待消息等导致阻塞的操作。它通常先被调度进入运行态，再在执行过程中因等待事件进入阻塞态。

整条因果链可以收束为：**具备运行条件并获得 CPU，进程由就绪态进入运行态；仍可运行但失去 CPU，进程回到就绪态；执行中必须等待事件，进程进入阻塞态；事件完成使其重新具备运行条件，进程回到就绪态。**
