# 课程生成效率优化方案

> 状态：待用户确认，本文档只做方案设计，未修改业务代码  
> 编写日期：2026-08-28  
> 目标：在不降低课程事实正确性、答案一致性和硬校验可靠性的前提下，降低“继续生成一节课”的等待时间  
> 当前基线：用户最近两次单节生成约 9 分钟、7.5 分钟；本机历史单课成功任务约 3.7～27.1 分钟，中位数约 6.3～10.9 分钟（受旧队列重复执行/重试历史影响，不能直接当成功率）

## 1. 需求理解与优化边界

用户希望将单节课程生成从目前约 7.5～9 分钟进一步提速。目标不是把模型请求强行截断，而是减少不必要的模型输出、整包返工、重复检索和无效等待。

必须保持：

- 事实、公式、适用条件、例题步骤和自测答案的硬校验；
- 每个考点有自测覆盖；
- 生成失败显式报错，不能用低质量模板伪装成功；
- 已完成课程检查点可复用；
- 单进程单 worker、同课程写入互斥和 lease fencing；
- 当前流式请求的首 token 保护、主备 failover 和取消语义。

本方案不建议：

- 简单把模型总超时从 1800 秒调小；
- 取消硬校验；
- 把模型失败改成“凑合内容”；
- 直接开多个 worker 并行写同一 workspace；
- 没有真实数据支撑就承诺固定成功率或固定耗时。

## 2. 当前生成链路与耗时来源

### 2.1 单节增量的实际路径

`approve_strategy_documents(generation_mode=incremental, lesson_limit=1, continue_generation=true)`：

1. 读取 workspace 和已批准策略；
2. 扫描资料、同步知识库、检索全课程证据（最多 20 段）；
3. 复用 workspace 任务计划，不重新调用 content planner；
4. 选择下一节未完成任务；
5. 本节检查点复用尝试；
6. 重新检索本节资料（最多 8 段）；
7. 模型生成完整讲义 JSON；
8. 本地硬校验；硬伤则再次生成完整讲义 JSON；
9. 模型根据完整讲义生成完整自测 JSON；
10. 本地硬校验；硬伤则再次生成完整自测 JSON；
11. 写入 lesson checkpoint、preview 和 workspace；
12. 若生成全部课程，才额外生成模拟卷，增量单课通常不走这一步。

主要证据：

- 计划复用和全课程检索：`backend/app/agents/content_workflow.py:81-183`；`backend/app/study_service.py:970-992`。
- 单节检索、完整讲义结构和输出：`backend/app/agents/lesson_generation.py:88-152`；`backend/app/agents/content_prompts.py:22-49`。
- 讲义硬校验与整包第二次生成：`backend/app/agents/lesson_generation.py:185-215`。
- 完整自测生成与硬校验返工：`backend/app/agents/lesson_generation.py:217-289`。
- 单 worker/lease/Job 超时：`backend/app/agent_runtime.py:25-30`、`650-760`。

### 2.2 影响 7.5～9 分钟的因素

#### A. 模型首要因素：输出 token 数和思考时间

讲义 Prompt 要求一次返回完整的故事版结构：四小节、多个 explanation beats、例题和变式、故事上下文、考点卡片、公式条件、来源等。输出是大 JSON；故事版还要维持叙事连续性，容易让思考型模型输出更长、等待更久。

自测是第二次独立大 JSON 调用。两次调用严格串行，因此耗时近似：

`讲义调用时间 + 自测调用时间 + 本地检索/落盘 + 重试等待`。

相关 Prompt：`backend/app/agents/content_prompts.py:22-55`。

#### B. 硬校验返工的放大效应

正常为讲义 1 次 + 自测 1 次；任一硬校验失败就整包重生成，最多可到 4 次逻辑模型调用。一次遗漏字段会丢弃几分钟的大 JSON 产出。

对应：`backend/app/agents/lesson_generation.py:146-215`、`223-289`。

#### C. 流式请求内部重试和主备切换

单次逻辑调用还可能触发 HTTP 重试、连接级最多 6 次重试、退避和主备 provider failover。正常慢模型不一定是故障，但失败窗口会放大耗时。

对应：`backend/app/model_client.py:31-74`、`663-741`。

#### D. 重复的本地检索/同步/数据库 I/O

每个增量 Job 都会：

- 扫描课程资料；
- 同步知识库；
- 全课程检索最多 20 段；
- 再做当前小节检索最多 8 段。

这些通常不是 7～9 分钟的主体，但会增加固定前置成本，并给模型输入增加无关上下文。

对应：`backend/app/study_service.py:970-992`；`backend/app/agents/lesson_generation.py:113-140`。

#### E. 本地排队和课程锁

单 worker 使队列等待、同课程锁等待、前一次任务未释放成为额外时间。当前 Job 记录创建/更新，但需要按阶段测量才能知道用户看到的 9 分钟究竟包含多少排队。

#### F. 统计与版本因素

历史 22～45 分钟记录受旧队列重复执行和多次 claim 影响，不能代表当前版本。最近样本约 7.5～11 分钟，说明当前主要瓶颈更可能是两次大模型串行调用，而不是旧队列问题。

## 3. 优化目标与可观测指标

在实施优化前和每次优化后，记录以下阶段：

- queue_wait_seconds：入队到 claim；
- preparing_seconds：扫描/知识库同步/检索；
- lesson_guide_model_seconds：讲义模型调用；
- lesson_guide_repair_seconds：讲义修复调用；
- lesson_questions_model_seconds：自测模型调用；
- lesson_questions_repair_seconds：自测修复调用；
- checkpoint_write_seconds：检查点与 workspace 写入；
- transport_retry_count / provider_failover_count；
- prompt_chars / evidence_chars / output_chars；
- final status 和本节是否首次/缓存复用。

不能只比较 Job 总时长，否则无法判断是模型慢、返工多、排队长还是本地 I/O 慢。

## 4. 推荐优化路线

### 阶段 0：先建立可比较基线（低风险，优先）

1. 将阶段耗时和调用次数持久化到 Job progress/result 或独立轻量 telemetry；不要只依赖进程内存 modelUsage。
2. 每次模型调用记录 stage、taskId、attempt、provider、开始/结束时间、输入/输出字符数、是否命中重试。
3. 在完成摘要和日志中显示本批阶段耗时。
4. 连续采集至少 5～10 次真实单课任务，按 contentStyle、provider、是否修复分别统计中位数/P75。

收益：不能直接减少单次耗时，但能避免盲目调参，明确 9 分钟主要花在哪里。

风险：增加少量数据库写入和实现复杂度。建议只在每个调用开始/结束写轻量记录，不保存完整 Prompt/答案，避免数据膨胀和隐私泄露。

### 阶段 1：修复失败后局部补丁，不再整包重生成（高收益，中风险）

#### 1A. 讲义结构局部修复

当前硬校验失败时再次返回整个 `studyGuide`。改为：

- 先把硬伤按路径分组：结构字段、考点卡、例题、故事段落、公式；
- 对能确定性补齐的字段由本地完成；
- 对需要模型判断的字段，只发送原稿中相关子树和硬伤列表；
- 模型返回 JSON Patch/局部子对象；
- 合并到原稿后重新跑全部硬校验；
- 合并失败仍显式失败，不降级。

第一期只做低风险局部范围：

- 缺失数组项/字段；
- 结构化过渡字段；
- 自测 ID、taskId、examPointIds 等确定性元数据。

公式、答案、事实矛盾不要本地猜测，必须交给模型修复并重新校验。

#### 1B. 自测缺覆盖时只补缺失考点题目

当前一个考点覆盖缺失会重新生成整套自测。改为：

- 保留已有合法题目；
- 计算缺失的 examPointIds；
- 只向模型请求缺失考点的 1～2 道题；
- 合并、去重、重新检查答案一致性和全覆盖；
- 若补题仍失败，明确失败。

这是最推荐的第一项效率改造，因为不会重新生成已经合格的题目。

预计收益：减少因覆盖漏项导致的第二次长调用；在发生返工的任务上可能节省 2～5 分钟，正常任务不增加调用。

### 阶段 2：缩小本节模型输入，保持事实覆盖（中高收益，中风险）

当前本节 Prompt 包含：

- 整个课程基本信息；
- 当前任务；
- 当前知识点；
- 前一节 highlights/storyContext；
- 下一节标题；
- 最多 8 段资料检索上下文；
- 完整课程 Prompt 和用户强反馈指令。

优化原则：

1. 保留当前任务、当前知识点、当前节必要资料证据；
2. 故事版只保留前一节衔接所需的最小摘要，不传完整 previousStoryContext；
3. 将全局 coursePrompt 中与当前课无关的内容拆分为结构合同、事实规则和本节指令；
4. 对 evidence 做去重、按相关性排序和字符上限；
5. 讲义和自测只传各自需要的字段。

必须通过 A/B 对比验证：

- 来源覆盖率不能下降；
- 公式/答案一致性不能下降；
- 硬校验失败率不能上升；
- 故事版连续性不能明显下降。

不建议未经测量直接大幅截断资料上下文或删除用户强反馈。

### 阶段 3：减少串行长调用（高收益，高风险，后置）

候选方案按风险从低到高：

#### 3A. 讲义成功后自测使用更轻量模型

若主模型和备用模型配置允许，可为自测配置独立 provider/model。自测输入已是结构化讲义，任务比讲义写作简单；先通过离线/真实小样本验证答案一致性和覆盖率，再启用。

优点：不改变业务流程，可能明显降低自测等待。  
风险：模型能力不足导致答案/解析问题增加；硬校验仍会失败并触发补题。

#### 3B. 合并讲义和自测为一次调用

一次返回 studyGuide + practiceQuestions，再本地同时校验。

优点：减少一次模型前置思考和网络连接成本。  
风险：输出 JSON 更大、模型更容易漏字段；失败时损失更大；故事版结构复杂度明显上升。

不建议作为第一步，只有阶段 0～2 数据证明串行调用是绝对瓶颈、且小样本质量稳定后再做实验分支。

#### 3C. 讲义与自测并行

理论上可以在已有讲义上下文基础上并行，但自测依赖讲义，无法真正并行；除非改为同一输入分别生成，会造成自测与最终讲义不一致，不推荐。

### 阶段 4：优化重试和缓存策略（中收益，需谨慎）

1. 对明确不可重试的 401/余额不足/模型不存在，立即停止，不吃连接重试预算。
2. 对确定性 JSON 解析错误做一次短修复请求，但不要将事实硬伤视为格式问题。
3. 强化讲义和自测 checkpoint 签名，保证 Prompt/资料未变化时 100% 复用。
4. 为 evidence 检索结果做按资料版本的缓存；资料未变时复用本节检索，避免重复 SQLite/FTS 工作。
5. 不降低流式首 token 30 秒保护和读流上限，不用缩短总超时冒充提速。

### 阶段 5：本地 I/O 和队列细化（低到中收益）

1. preparing 阶段合并/缓存 scan + sync + 全局 retrieval；
2. 任务级知识库版本不变时跳过重复同步；
3. 完成 checkpoint 后只更新必要 workspace 字段；
4. 提供 queue wait 与 running wait 分开统计；
5. 保持单 worker，不进行多个 uvicorn worker 并发写入。

## 5. 推荐实际落地顺序

### 第一轮（建议优先批准）

只实施低风险、高确定性变更：

1. 阶段耗时/调用/输入输出规模基线记录；
2. 自测覆盖缺失时的增量补题；
3. 明确区分“首次生成”和“修复/继续生成”缓存命中；
4. 真实采集 5～10 次后再判断下一轮。

预期：正常任务耗时基本不变；返工任务减少 2～5 分钟；不牺牲质量。

### 第二轮

根据第一轮数据选择：

- 本节 evidence 精简和去重；
- 故事版衔接上下文压缩；
- 自测独立轻量模型；
- 资料检索和知识库同步缓存。

### 第三轮实验

仅在 A/B 样本证明安全后评估：

- 合并讲义+自测一次生成；或
- 更改生成协议为结构化工具调用/分块输出。

## 7. 风险与回滚

- 所有结构化输入输出改动必须有旧合同回退开关；
- 任何阶段硬校验失败率上升时，立即关闭实验开关；
- 保留旧 checkpoint 格式兼容读取；
- 不改真实课程历史数据；
- 不提交 `backend/.env` 或 `backend/data/`；
- 每一轮一类改动一个 commit，由用户本人提交；
- 当前工作区有课程反馈相关未提交改动，实施时只触碰列明文件并先检查 diff。

## 8. 测试与验收

### 自动测试

每轮改动后运行：

`cd backend; .\.venv\Scripts\python.exe -m pytest tests -q`

若改动 web，追加：

`cd web; npx tsc -b`  
`cd web; npm run build`

第一轮至少新增：

1. 合法已有自测题保留；
2. 缺少一个考点时只请求缺失考点补题；
3. 补题合并后通过全覆盖和答案一致性校验；
4. 补题再次失败时显式失败；
5. stage telemetry 能区分首次/修复/缓存命中；
6. 旧 checkpoint 和新字段兼容；
7. 资料/Prompt 未变时 checkpoint 复用不调用模型。

### 真实验收矩阵

每种 contentStyle（standard/dialogue/story）至少各 3 次单课：

- 总耗时；
- queue wait / preparing / 讲义 / 自测 / 写入；
- 模型调用次数；
- 修复次数；
- 来源覆盖率；
- 公式和答案一致性；
- 课程前后顺序与故事连续性；
- 失败是否明确，不得降级成功。

第一轮目标不是承诺所有任务都低于某个固定分钟数，而是：

- 正常无返工任务：不比当前基线明显变慢；
- 发生覆盖返工任务：少一次完整自测生成；
- 质量硬指标不下降；
- 阶段耗时数据完整可解释。

### 完成定义

- 有 5～10 次真实任务可比较阶段数据；
- 增量补题通过自动测试和真实三种风格验收；
- 硬校验、答案一致性、来源覆盖率不下降；
- 失败仍显式报错；
- 用户能从状态卡看到调用/修复次数与耗时；
- 不使用低质量兜底、不降低超时安全边界、不增加 worker 并发。

## 9. 建议用户确认项

建议先批准“第一轮低风险优化”，而不是一次性批准所有高风险实验：

- [ ] 同意先建立阶段耗时基线，真实采集 5～10 次；
- [ ] 同意自测覆盖缺失时改为只补缺失考点题目；
- [ ] 同意保留全部硬校验和显式失败原则；
- [ ] 暂不启用合并讲义+自测、并行生成或直接调小总超时；
- [ ] 同意根据第一轮数据再决定上下文裁剪、轻量模型或合并调用实验。
