# 午间订单流转时，状态箭头怎样移动

小程面对刚离开封口机的订单，先检查它是否仍具备继续处理的条件。若条件仍齐全，它只是在等下一次使用封口机，对应就绪态；若它必须等待珍珠煮好等事件，对应阻塞态。映射回进程：**离开 CPU 后能立即继续执行，只是尚未获得 CPU，进入就绪态；必须等待某个事件发生才能继续，进入阻塞态。**

## 三张订单为什么对应三种状态？

判断进程状态可沿两个问题进行：

1. **它是否正在占用 CPU？**正在占用并执行，就是运行态。
2. **若没有占用 CPU，现在给它 CPU 能否立即继续？**能，就是就绪态；不能，还要等待事件，就是阻塞态。

| 状态 | 是否占用 CPU | 是否已具备运行条件 | 奶茶店映射 |
|---|---:|---:|---|
| 运行态 | 是 | 是 | 正在使用封口机 |
| 就绪态 | 否 | 是 | 材料齐全，只等封口机 |
| 阻塞态 | 否 | 否 | 缺少材料，等待补齐 |

“没占 CPU”不能单独决定状态，因为就绪态与阻塞态都不占 CPU；两者的分界是能否立即继续执行。

## 材料齐全的订单何时开始处理？

调度程序从就绪进程中选中一个并分配 CPU，发生：

**就绪态 → 运行态：被调度并获得 CPU。**

店员从材料齐全的排队订单中选出一张放上封口机，准确对应这个过程。就绪只表示可以运行，只有真正获得 CPU 才进入运行态。

易错边界：I/O 完成或资源可用通常解除阻塞，使进程进入就绪态；它们本身不等同于进程已获得 CPU。

## 时间片结束后，订单去了哪里？

某进程正在运行，时间片用完，或者被更高优先级进程抢占。它失去 CPU，但仍具备继续执行条件，发生：

**运行态 → 就绪态：时间片用完或被抢占，失去 CPU 但仍可运行。**

故事中可以把它理解为店员暂时把尚可继续处理的订单放回可处理队列。决定方向的条件是订单仍可继续，映射回术语就是进程仍具备运行条件。

易错边界：离开 CPU 不等于进入阻塞态。只有等待某事件、暂时无法推进时，才进入阻塞态。

## 缺少珍珠时，为什么不能继续占用封口机？

正在处理的订单发现珍珠尚未煮好，只能等待。对应运行进程执行到必须等待的 I/O、资源、信号量或消息等事件，即使继续占有 CPU 也无法推进，发生：

**运行态 → 阻塞态：正在执行的进程等待某事件。**

这里的决定性条件是“事件未发生前不能继续执行”。时间片用完与被抢占没有造成这种条件缺失，因此应与本箭头区分。

## 珍珠煮好后，订单会立刻占用封口机吗？

珍珠煮好，只说明等待条件解除。订单材料重新齐全，但封口机可能仍被另一张订单占用，它需要回到可处理队列。对应：

**阻塞态 → 就绪态：等待事件完成，进程被唤醒并重新具备运行条件。**

被唤醒表示“可以运行”，获得 CPU 才表示“正在运行”。因此，除非题干明确说明随后立即被调度并获得 CPU，否则不能把事件完成直接写成进入运行态。

## 哪两条箭头通常不能直接画？

基础三态模型的直接转换关系如下：

```text
就绪态 --被调度、获得 CPU--> 运行态
运行态 --时间片用完或被抢占--> 就绪态
运行态 --等待 I/O、资源等事件--> 阻塞态
阻塞态 --事件完成、被唤醒--> 就绪态
```

还有两条通常不能直接发生：

- **阻塞态 ⇏ 运行态**：事件完成只使进程重新具备运行条件，通常要先进入就绪态，再等待调度。若题干明确说明唤醒后立即被调度，应把它理解为连续发生“阻塞态→就绪态→运行态”两步。
- **就绪态 ⇏ 阻塞态**：就绪进程没有占用 CPU，通常无法执行请求 I/O、申请资源或等待事件等导致自己阻塞的操作。它通常要先被调度进入运行态，执行相关操作后才可能阻塞。

## 小程怎样逐步判定一条箭头？

1. 先确定事件发生前的状态，尤其检查进程是否正在占用 CPU。
2. 再检查事件发生后是否具备运行条件：仍可执行则考虑就绪态，必须等事件则考虑阻塞态。
3. 最后检查是否明确获得 CPU；只有获得 CPU 才进入运行态。
4. 写箭头时同时写触发事件，避免把调度、抢占、等待和唤醒混在一起。
