# 午间高峰记录：把事件逐项落到箭头上

判断状态变化时，小程按同一顺序检查：原状态是什么，事件是否改变运行条件，进程是否获得 CPU。下面先完成一条连续记录，再通过三个变式改变关键条件。

## 主例题：一张订单经历了哪些状态？

午间高峰中，用进程 P 对应一张订单。P 初始已经具备运行条件，正在等待 CPU。随后依次发生：

1. 调度程序选中 P；
2. P 运行一段时间后请求磁盘 I/O，必须等待 I/O 完成；
3. I/O 完成，系统唤醒 P，此时 CPU 正在运行另一个进程；
4. 调度程序再次选中 P；
5. P 的时间片用完，但仍可继续执行。

请写出完整状态链，并说明每一步的触发原因；同时指出其中是否出现了阻塞态直接到运行态。

### 第 1 问：P 的初始状态是什么？

**答案：就绪态。** P 已具备运行条件，但正在等待 CPU，符合就绪态的条件。

### 第 2 问：事件 1 后怎样变化？

**答案：就绪态 → 运行态。** 调度程序选中 P 并分配 CPU，P 从可以运行变为正在占用 CPU 执行。

### 第 3 问：事件 2 后怎样变化？

**答案：运行态 → 阻塞态。** P 正在运行时请求 I/O，并且必须等待 I/O 完成；等待期间即使获得 CPU 也无法继续推进。

### 第 4 问：事件 3 后怎样变化？

**答案：阻塞态 → 就绪态。** I/O 完成解除了阻塞原因，使 P 重新具备运行条件；CPU 此时由另一个进程占用，P 尚未获得 CPU。

### 第 5 问：事件 4 和事件 5 各对应什么？

**答案：事件 4 是就绪态 → 运行态；事件 5 是运行态 → 就绪态。** 再次被调度使 P 获得 CPU；时间片用完后 P 虽失去 CPU，但仍可继续执行，所以回到就绪态。

### 完整答案

**就绪态 → 运行态 → 阻塞态 → 就绪态 → 运行态 → 就绪态。**

触发原因依次为：被调度获得 CPU、等待 I/O、I/O 完成并被唤醒、再次被调度、时间片用完。链中没有阻塞态直接到运行态；I/O 完成与再次调度是两个独立事件，中间经过就绪态。

## 变式一：把“等待 I/O”改成“被抢占”

P 正在运行时，更高优先级进程到达，P 被抢占。P 没有等待 I/O 或资源。P 转入什么状态？

**答案：运行态 → 就绪态。** 抢占让 P 失去 CPU，但没有破坏它的运行条件；再次获得 CPU 后，它可以继续执行。把“离开 CPU”一律判为阻塞态会忽略运行条件仍然具备这一事实。

## 变式二：I/O 完成后能否一步写成运行态？

P 因等待磁盘 I/O 处于阻塞态。I/O 完成后系统唤醒 P，但题干没有说明调度结果。有人写出“阻塞态 → 运行态”。请纠正并解释。

**答案：应写为阻塞态 → 就绪态。** I/O 完成只解除等待条件，使 P 可以运行；题干没有说明 P 已获得 CPU。若之后调度程序选中 P，应再写一步“就绪态 → 运行态”。

## 变式三：就绪进程能否直接等待资源？

P 处于就绪态。题目直接写“P 申请不可用资源，因此由就绪态进入阻塞态”，且没有说明 P 先获得 CPU。这个路径在基础三态模型中是否成立？

**答案：通常不成立。** 就绪态进程尚未占用 CPU，通常不能执行申请资源并等待的操作。合理路径是先被调度，发生“就绪态 → 运行态”；随后在运行中申请不可用资源，发生“运行态 → 阻塞态”。若特殊题干另有明确规定，应以题干为准。

## 这组题实际训练了什么

每一步都先确认原状态，再判断事件是否让进程失去运行条件，最后检查是否明确获得 CPU。这样可以区分“时间片用完或被抢占”与“等待事件”，也能识别“阻塞态直接到运行态”和“就绪态直接到阻塞态”两条通常错误的捷径。下一份自测将减少故事提示，由你独立完成状态与箭头判断。
