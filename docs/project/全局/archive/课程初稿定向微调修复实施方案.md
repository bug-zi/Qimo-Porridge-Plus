# 课程初稿定向微调修复实施方案

> 状态：已获用户批准并进入实施；实现阶段一至三已完成，真实上游验收待进行
> 编写日期：2026-08-28
> 目标：将讲义和自测的二次处理从“重新生成完整内容”改为“基于初稿的定向微调”，减少重复输出与等待，同时保留事实、公式、答案和来源等质量底线。

## 1. 现状分析

当前单节流程由 backend/app/agents/lesson_generation.py 的 LessonBuilder.build 负责：

1. 无有效 checkpoint 时，第一次完整生成 studyGuide；
2. 对初稿执行 _study_guide_issues 和 _strong_feedback_issues；
3. 存在 blocking issue 时，再调用同一个完整讲义生成函数，并要求模型重新返回完整 studyGuide；
4. 基于最终讲义第一次完整生成 practiceQuestions；
5. 对自测执行 _question_issues 和考点覆盖校验；
6. 存在 blocking issue 时，再要求模型重新返回整套 practiceQuestions。

关键代码位置：

- 讲义调用与 repair：backend/app/agents/lesson_generation.py:146-215
- 自测调用与 repair：backend/app/agents/lesson_generation.py:223-289
- hard/soft 分类：backend/app/agents/content_validation.py:42-70
- 故事版 Prompt：backend/app/agents/content_prompts.py:22-49
- 自测 Prompt：backend/app/agents/content_prompts.py:51-56

当前问题是：第二次请求虽然带有 reviewIssues，但仍要求完整输出。这样会重新表达已经正确的故事、考点、公式、例题和衔接内容，产生大 JSON、更多 token 和更长等待，并可能误伤初稿中原本正确的部分。一次局部字段遗漏不应导致整份初稿被丢弃。

另有两个边界：readability_review.py 只写入辅助审核报告，不参与 LessonBuilder repair；软伤不应触发模型调用；生成失败仍须显式报错，不能恢复低质量兜底。

## 2. 需求理解

本方案按以下原则改造：

- 第一次模型调用负责完整创作，是质量主体；
- 后续调用只负责针对校验问题微调、补缺和润色；
- 未命中的字段、故事主线、事实、公式、题目条件和答案尽量原样保留；
- 修复请求不再返回完整讲义或完整题目集合；
- patch 合并后仍执行完整硬校验；
- 修复失败显式失败，不用凑合内容假装成功；
- 现有 checkpoint、取消、lease fencing、同课程互斥和 workspace 合并契约保持兼容。

## 3. 目标方案

### 3.1 讲义

初稿完整生成 → 定位 blocking issue → 发送初稿相关局部上下文和字段路径 → 模型返回 GuidePatch → 服务端安全合并 → 完整硬校验 → 保存最终讲义。

修复请求只允许返回有限的补丁，例如：

{
  "patches": [
    {"op": "replace", "path": "sections[1].explanationBeats[2].conclusion", "value": "修正后的结论"}
  ]
}

操作建议只允许 replace、add、remove；remove 只有在明确结构冗余且不破坏硬合同的情况下允许。不能接受任意自由文本或整份 studyGuide。

### 3.2 自测

自测初稿完整生成 → 定位到题目 ID、考点 ID和字段 → 模型返回 QuestionPatch → 服务端合并 → 答案一致性处理、选项规范化和完整硬校验 → 保存最终自测。

自测 patch 支持：

- 修改目标题目的 explanation、prompt、options、answerIndex 等字段；
- 补充缺失字段；
- 只为未覆盖考点新增一道题；
- 删除明确非法题并用新题替代。

合法题目默认保留，不因一题问题而重做整套题。

## 4. 实施步骤

### 阶段一：新增安全 patch 协议和合并器

新增 backend/app/agents/content_patches.py，负责：

- 定义讲义 patch、自测 patch 的结构化协议；
- 校验 task、question、examPoint 的定位；
- 路径白名单和不可修改字段白名单；
- 限制 patch 数量、路径深度、文本长度和新增数组项数量；
- 在副本上应用 patch，失败时不污染初稿；
- 重新规范化 question id、taskId、knowledgePointId 和单选题答案下标；
- 无效 patch 显式报错。

禁止 patch 修改：任务计划、task.id、question.id、taskId、知识点关联、资料来源和未授权章节。具体白名单在实现阶段依据实际数据结构确定，不直接开放任意 JSON Pointer。

### 阶段二：接入讲义定向修复

修改 LessonBuilder 的讲义修复分支：

1. 第一次仍使用完整 LESSON_CONTENT_PROMPT；
2. 将 blocking issue 转换为带字段路径的 repair targets；
3. 新增 LESSON_CONTENT_PATCH_PROMPT，明确这是编辑任务，不是重新创作；
4. 输入初稿相关片段、问题路径、资料证据和最小故事连续性上下文；
5. 模型只返回 patches；
6. 服务端合并 patch，并对完整讲义重新执行原有校验；
7. 仍有硬伤则显式失败，不再退回整份完整重生成；
8. 仅剩软伤则接受并记录。

建议的定向处理：

- 缺字段：只补字段；
- 缺 conceptMappings：只补映射项；
- 缺衔接文案：只补 transition 字段；
- 公式缺 meaning 或 conditions：只补公式上下文；
- 过程型考点未被例题覆盖：只补 examPointIds 或最小例题内容；
- storyEventRef 只是自然语言措辞不同：优先接受或使用本地关联，不重写正文；
- 数量、顺序和措辞软伤：不发送 patch。

### 阶段三：接入自测定向修复

修改自测 repair 分支：

1. 第一次仍根据最终讲义生成完整自测集合；
2. 保留所有合法题目；
3. 将问题定位到题目 ID、考点 ID和字段路径；
4. 新增 LESSON_PRACTICE_PATCH_PROMPT，只要求修改目标题或新增缺失考点题；
5. 合并后运行 _question_issues、考点覆盖校验、答案一致性和选项规范化；
6. 仍有硬伤则显式失败，不整套重生成。

自测缺一个考点时，优先保留已有题并只生成缺失考点题。这与现有 docs/课程生成效率优化方案.md:141-170 的增量补题方向一致。

### 阶段四：checkpoint、进度和日志

区分以下阶段：

- initial：完整初稿；
- patch：局部微调；
- accepted：初稿或 patch 后通过；
- failed：patch 后仍有硬伤。

建议增加以下可观察字段：repairMode=patch、patchCount、patchedPaths、initialIssueCodes、remainingIssueCodes，以及初稿和 patch 的输入输出规模。旧 checkpoint 继续按现有格式读取，新字段采用可选兼容方式。

### 阶段五：测试与真实验收

至少新增测试：

1. 合法初稿不调用 repair；
2. 讲义单字段问题只发送 patch 请求；
3. 未指定讲义字段深度保持不变；
4. patch 不能越权修改任务、来源、知识点和其他章节；
5. patch 后通过原有硬校验；
6. 无效路径显式失败；
7. patch 后仍有硬伤显式失败且不产生低质成功内容；
8. 自测缺考点时只新增缺失考点题；
9. 单题问题只修改目标题；
10. 合法自测题修复后保持不变；
11. 选项洗牌后答案下标保持一致；
12. patch 后 checkpoint 能正常保存和复用；
13. 旧 checkpoint 继续兼容；
14. 取消、fencing、互斥和 workspace 合并行为不变；
15. 故事版软伤不触发 patch。

真实验收采集至少 5～10 次单节任务，比较讲义初稿耗时、patch 耗时、自测初稿耗时、patch 次数、patch 输出规模、总耗时、patch 后通过率、事实/公式/答案/来源覆盖率和故事连续性。

## 5. 影响范围

预计修改：

- backend/app/agents/lesson_generation.py：改讲义和自测 repair 流程；
- backend/app/agents/content_prompts.py：增加两个 patch Prompt；
- backend/app/agents/content_patches.py：新增协议和安全合并器；
- backend/app/agents/content_validation.py：必要时补充带路径诊断，不降低质量底线；
- backend/app/agents/checkpoint_contracts.py 或类型模块：必要时增加可选 patch 元数据；
- backend/tests/：新增协议、合并器、LessonBuilder 和回归测试；
- docs/DEV_BOARD.md：跟踪实施和验证。

本轮不修改 backend/data、backend/.env、前端、模型超时、流式首 token 保护、worker 架构和队列 fencing。

## 6. 风险与兼容性

### 风险一：patch 格式错误

使用严格结构化解析、路径白名单和失败即报错，不接受完整对象冒充 patch。

### 风险二：局部修复破坏跨字段一致性

patch 后继续执行完整硬校验；服务端负责 ID、taskId、考点关联和答案下标规范化。

### 风险三：初稿损坏过重

如果整个 studyGuide 缺失、核心章节大面积为空或初稿无法解析，不强行局部修复，直接显式失败并保留失败 artifact。是否允许用户手动重新生成，应作为独立操作，不在 repair 分支隐式发生。

### 风险四：模型修改超出目标范围

只发送最小上下文，要求返回明确路径；服务端拒绝未授权路径；测试深比较未指定字段。

### 风险五：patch 不一定天然更快

必须记录初稿和 patch 的耗时、输出规模与通过率。如果 patch 失败率过高，先调整 patch 协议和上下文，不直接降低硬校验。

### 风险六：旧数据兼容

旧 checkpoint 继续读取完整 studyGuide/practiceQuestions；新协议仅用于新的 patch artifact，最终仍保存现有完整内容结构。

## 7. 验收标准

### 功能

- 初稿通过硬校验时不触发 repair；
- 发生局部硬伤时 repair 只返回 patch；
- 未指定字段不被修改；
- patch 后完整硬校验通过才接受；
- patch 后仍失败则显式报错；
- 不恢复低质量降级模板；
- 故事版软伤不触发 patch；
- 自测缺考点时只补缺失题；
- 旧 checkpoint、取消、fencing、互斥和 workspace 合并兼容。

### 性能

通过真实样本验证：

- patch 输出规模明显小于完整重生成；
- 发生修复时总等待时间下降；
- 无修复任务不比当前基线明显变慢；
- patch 后通过率不低于当前基线。

### 质量

以下指标不得下降：

- 资料来源覆盖；
- 公式表达、含义和适用条件；
- 例题步骤完整性；
- 自测答案与解析一致性；
- 自测考点覆盖；
- 故事连续性；
- 失败显式性。

## 8. 需要用户确认的事项

1. 是否同意修复阶段只返回局部 patch，不返回完整讲义或整套自测；
2. 是否同意 patch 只执行一次，仍有硬伤就显式失败，不隐式整包重生成；
3. 是否同意保留事实、公式、答案、来源和考点覆盖硬校验；
4. 是否同意 readabilityReview 继续只做辅助审核，不新增模型修复调用；
5. 是否同意自测优先保留合法题目，只补缺失考点题；
6. 是否同意先实施 patch 协议、讲义 patch、自测 patch，再依据真实数据继续调整数量型规则。
