课程划词反馈核心链路已经由用户完成真实课程验证，当前实现具备：

- 前端选区、结构字段和上下文组装；
- submit → 分析 → rewrite proposal → 前端预览；

- accepted / abandoned 会话压缩；
- proposed / active / inactive 规则生命周期；
- 课程偏好查看、启用、停用、删除、合并；
- 未确认、失败、放弃的反馈不进入后续生成强指令。

已知验证结果：后端全量测试 173 passed；前端 Vitest 5 passed；前端 TypeScript npx tsc -b 通过；真实课程反馈效果链用户确认通过；后端 8000 OpenAPI 已确认反馈生命周期路由注册；git diff --check 通过。

项目已从反馈核心修复阶段进入“核心链路稳定、工程质量和全局验收待补齐”阶段。工作区仍有用户或并行任务的未提交改动，尤其涉及 agent runtime、content workflow、lesson generation、study service、App.tsx、ModuleView.tsx、课程生成状态和用量统计。后续实施必须先用 git status --short 和对应 git diff 确认归属，不能覆盖这些改动。

## 2. 仍存在的主要问题与优先级

### P0：没有新的阻断性反馈 Bug

真实课程反馈已经通过，因此不再把划词反馈核心链路作为未完成 P0。除非后续出现回归，否则只做回归测试和数据观察，不继续扩大该功能范围。

### P1：完成现有代码的真实全链路验收

看板中仍未完成的真实验收包括：

1. 文字型 PDF/PPT：导入 → 策略 → 增量生成第一课 → 继续生成 → 学习 → 练习 → 错题/笔记；
2. 含公式理工科资料：公式、题目、解析正确性；
3. 扫描 PDF/图片：RapidOCR 和视觉兜底；
4. 标准版、对话版、故事版三种课程风格；
5. 模型超时、重试、主备切换和错误提示；
6. 上游挂起时后台队列释放、后续任务继续处理；
7. 队列 fencing 修复后的真实生成一轮，确认无重复执行。

这些项目需要真实模型、真实资料或人工操作，不能用 demo 模式代替。

### P1：定位 Windows Vite/Rolldown 构建失败

当前 npm run build 的已知结果是 TypeScript 检查通过，Vite 转换约 2249 个模块后退出 1，无 JavaScript 堆栈。下一步应记录 Node、npm、Vite、Rolldown 和 lockfile 版本，并逐项排除新增依赖、CSS、资源、大型模块和 Windows 环境因素。在定位前不得把 build 标记为通过，也不得为了绕过构建错误删除功能或降低质量。

### P1：补齐反馈 router 集成测试

反馈核心单测已经存在，但 router 集成覆盖仍需补齐：

- 无 token 返回 401；
- 非 owner 遵循既有 ownership 错误；
- retry / abandon / apply response shape；
- 不存在反馈、revision 冲突、输入校验分别返回 404/409/422；
- rewrite 部分失败不能伪装成整体成功；
- 响应字段与 web/src/types.ts 一致。

测试必须使用独立临时目录或 monkeypatch，不能读取、修改或清理真实 backend/data/。

### P2：反馈存储进一步做减法

当前已经完成课程级锁、原子写入、8 轮上限和 accepted/abandoned 压缩，但仍建议后续补强：feedback.jsonl 总量或保留期限、failed 状态错误分类与 payload 清理、最近 N 个完整候选限制、过期 open session 惰性清理、compact hash/摘要验证、规则冲突检测和 superseded 状态、规则价值淘汰。

这些属于可维护性增强，不应影响当前已验证的反馈主流程。

### P2：继续拆分大文件和补前端测试

study_service.py 仍有约 1660 行，ModuleView.tsx 仍是大型组件。应继续按职责抽取，禁止继续堆积新的顶层函数或组件。前端已有反馈 reducer 的 5 个 Vitest 测试，后续优先覆盖 generation job、课程生成状态卡、revision 冲突、课程偏好面板和选区上下文构造。

## 3. 推荐实施顺序

### 阶段 1：建立干净基线

1. git status --short；
2. 查看相关文件 diff，区分用户改动和待处理改动；
3. 确认后端显式重启方式，避免中文路径下 reload 使用旧代码；
4. 保存 pytest、tsc、Vitest、build 基线；
5. 不触碰真实 backend/data/。

完成标准：工作区归属清楚，验证结果和运行服务版本可追踪。

### 阶段 2：反馈契约集成测试

建立独立 router 测试 fixture，覆盖认证、owner、输入校验、submit、retry、refine、abandon、apply、删除 proposal、普通 rewrite、部分失败、revision 冲突和重复 apply，并将响应 shape 与前端类型锁定。

完成标准：反馈 API 的主要 HTTP 状态和响应字段由测试固定，且不污染真实数据。

### 阶段 3：构建问题最小化定位

记录工具链版本；比较完整构建、最小入口构建和临时副本构建；逐项排除依赖、CSS、资源和大型模块。若确认是上游原生问题，记录可复现命令、版本和替代验证方式。不在没有证据的情况下更换构建工具或删除功能。

完成标准：要么 build 通过，要么形成明确、可复现、隔离的上游问题记录。

### 阶段 4：真实课程生成验收

按看板 P1 清单，使用非破坏性测试课程或用户明确指定课程验证文字资料、公式资料、扫描资料、三种风格、超时重试 failover、队列 fencing 和挂起释放。每次记录课程 ID、job ID、输入类型、模型配置、结果和失败日志。除用户明确授权外，不删除或清理真实课程数据。

### 阶段 5：反馈数据维护增强

待集成测试和真实验收稳定后，再处理反馈保留期限、failed/open session 整理、compact 摘要与 hash、rule 冲突和 superseded、价值淘汰。SQLite 迁移仍是独立方案，必须先双读、备份验证和用户确认。

### 阶段 6：结构和测试债务

继续抽取 study_service.py 和 ModuleView.tsx，补新模块纯逻辑测试，完成前端 generation usage baseline 链路，补本地安装、依赖检查和启动文档。

## 4. 建议提交拆分

所有提交由用户本人执行，AI 不执行 commit。建议：

1. test(feedback): 补反馈路由集成契约测试；
2. fix(build): 定位并修复 Windows 前端构建失败；
3. test(generation): 补真实生成与队列验收覆盖；
4. feat(feedback): 增强反馈会话清理与规则维护；
5. refactor(study): 继续拆分剩余课程服务职责；
6. refactor(web): 拆分课程模块视图组件；
7. docs(dev): 补本地安装、验证和运行说明。

每一类改动独立运行适用的验证三件套，并在 docs/DEV_BOARD.md 记录结果。

## 5. 验收门槛

### 反馈 API

- 后端全量 pytest 通过；
- router 集成测试通过；
- 前端 tsc 和 Vitest 通过；
- 真实课程划词反馈不回归；
- 未确认规则不进入后续 Prompt。

### 前端构建

- npx tsc -b 通过；
- npm test 通过；
- npm run build 通过，或有独立、可复现并记录完整版本信息的上游原生失败说明；
- 不用 demo 结果替代真实后端验证。

### 真实生成

- job 只产生预期次数的 attempt；
- 同一课程不会有重复 running job；
- 心跳、lease fencing、取消点和终态摘要正常；
- 失败显示真实原因，不返回伪成功内容。

### 数据维护

- 所有测试数据使用临时目录；
- 真实数据只读，除用户明确授权不得清理；
- compact 可恢复、可解释、可回滚；
- 不把未确认反馈激活为规则。

## 6. 当前不做

本计划不包含课程广场、管理后台、云部署、公网服务、多租户运营、PostgreSQL、Redis、Celery、对象存储、未经独立方案确认的 SQLite 迁移，也不通过降低课程生成质量或隐藏真实失败来规避构建错误。
