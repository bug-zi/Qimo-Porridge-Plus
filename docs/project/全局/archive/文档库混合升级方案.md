## 2. 需求理解

### 2.1 并入机制与落点

| 机制 | 落点 | 规则要点 |
|---|---|---|
| 问题疑惑区 | `docs/project/questions.md`（单文件区，英文文件名遵守宪法 §3，内容标题中文） | 用户记录对代码/设计/文档的疑惑；**AI 不主动查阅**，仅用户指名时读取答疑；解答后整轮移入文件内「已完成区」 |
| 域内 spec/plan | `modules/<域>/` 或 `core/<域>/` 下 `YYYY-MM-DD-<主题>-design.md` + `-plan.md`（主题用中文短语，与 proposals 命名实践一致；日期前缀保证唯一可排序） | spec=本次功能设计定稿记录；plan=实施计划，头部 **Spec:**/**Plan:** 互指；plan 顶部状态行（进行中/已落地/已废弃+原因）；小改动可只有 design 无 plan |
| 域内归档 | `<域>/archive/`（不预建，随第一份归档产生） | spec/plan 落地或废弃后成对移入，**不改名不删除** |
| 按轮归档 | questions.md 内部 | 答完一轮 → 「已完成区」顶部新增 `### 第N轮（YYMMDD）：<主题>`，条目保留原始描述 + 问答全文；N 从 1 起全项目连续编号只增不减，新轮插最上方 |
| 归档固定四步 | 宪法明文化 | ① `mv` 入 archive/ 不改名 → ② 文档顶部状态区追加 `- 已归档：YYMMDD 随 <主题> 落地/废弃（原因）` → ③ 全库检索旧路径、更新活动文档引用（历史日志不改）→ ④ 当日日志记一笔 |
| 永不删除原则 | 宪法明文化 | 归档只是位置变化，体系内文件永不删除；废弃由用户明说，AI 不自行判定 |
| 日志创建时间行 | 宪法 §4.2 补充 | 每个 log 二级标题（会话小节）下首行 `> 创建于 YYYY-MM-DD HH:MM`（date 命令实取，不估不编） |

### 2.2 spec/plan 与既有文档的边界（关键设计）

- **proposals/**：用户发起的变更方案正本渠道（现状分析/需求理解/影响范围/风险，供用户审阅决策），系统级或跨域。宪法级流程不变。
- **域内 spec/plan**：立项后 AI 的设计过程文档（单域功能级），从 proposals 或看板任务立项产生。
- **域 design.md / designs-specs.md**：契约与事实的沉淀层。spec/plan 是过程文档，落地时耐久结论按 §2.2 回流规则并入 design.md（决策）与 designs-specs.md（事实），spec/plan 本体归档。
- **DEV_BOARD.md**：仍是任务状态唯一真源（做什么了）；spec/plan 承载内容（为什么这么做、怎么做）。互补不重复。

### 2.3 明确不并入项

- 新功能开发区.md / 优化建议区.md：ideas.md + proposals/ 已覆盖，再建会形成三头入口，破坏现有「灵感 → 提案 → 落地 → 沉淀」单线流程。
- 临时草稿（待写入）.md：ideas.md 已承担。
- docs/log/ 根级日志、YYMMDD.md 命名：现有 YYYY-MM-DD.md 更符合本项目双库对称习惯。

## 6. 风险与兼容性

- 纯文档变更，无代码风险；验证三件套不适用（无代码改动），以文档核验代替
- 现有流程零破坏：ideas / proposals / log / 看板 / bugs / study 机制原样保留
- 命名合规：questions.md 沿用系统文件英文命名惯例（同 bugs.md / ideas.md），规避非 ASCII 路径工具链问题
- spec/plan 引入双渠道风险已由 §2.2 边界划定消除
- skill 后续再调用时，本方案即为「已按项目适配」的凭证，不会重复触发改名前置
